# Лабораторная работа «Предварительная обработка»

Программа лабораторной работы «Исследование эффективности устройств
предварительной обработки радионавигационных систем».
ВКА имени А.Ф. Можайского, кафедра космической радиолокации и радионавигации.

Заменяет прежнюю программу `Obr rabot.exe` (Compaq Visual Fortran, 2009 г.).

## Состояние разработки

Все четыре шага выполнены.

| Шаг | Содержание | Состояние |
|---|---|---|
| 1 | Каркас программы и входной контроль знаний | готово |
| 2 | Ввод исходных данных, таблица вариантов, контроль допустимости | готово |
| 3 | Расчётное ядро (МНК, ошибки оценивания) со сверкой по эталону | готово |
| 4 | Экран результатов, иллюстрации, рабочая тетрадь, отчёт, режим преподавателя | готово |

Осталось после отработки: убрать режим совместимости с прежней программой.

## Требования

Только JDK 11 или новее. Внешних библиотек нет: используется стандартная
библиотека Java и Swing, графики программа рисует сама. Поэтому проект
собирается на любой машине, в том числе без доступа в интернет
(при первой сборке Maven загружает только свои штатные плагины).

## Сборка и запуск

Из NetBeans: «Открыть проект», выбрать папку `upo-lab1`, затем «Запустить».
Формы (`*.form`) открываются в визуальном конструкторе.

Из командной строки:

```
mvn clean package
```

Сборка сама складывает в папку `target/dist` всё, что нужно для переноса
программы на другой компьютер: `upo-lab1.jar`, файл `Настройки.properties`
(из корня проекта – так же, как его читает программа при запуске из-под
NetBeans) и файл `Запуск.bat` (источник – `src/main/dist/Запуск.bat`).
Для компьютерного класса достаточно скопировать папку `target/dist`
целиком и установить среду выполнения Java 8 или новее. Запуск – двойным
щелчком по `Запуск.bat` (он же проверяет, установлена ли Java, и ждёт
нажатия клавиши, если программа завершилась с ошибкой) или командой
`java -jar upo-lab1.jar` из этой папки.

При настройке рабочих мест удобно вынести на рабочий стол ярлык на
`Запуск.bat` со значком программы: сам `.bat`-файл своей иконки не несёт,
поэтому в свойствах ярлыка («Изменить значок…») нужно указать файл
`Эмблема кафедры.ico` из той же папки `target/dist` (PNG для этого не
подходит – проводник Windows принимает в качестве значка ярлыка только
`.ico`, `.exe` и `.dll`).

### Запуск в Linux (в том числе в Астра-Линукс)

Рядом с `Запуск.bat` кладётся `Запуск.sh` – то же самое для Linux. Перед
первым запуском ему один раз даётся право на исполнение:

```
chmod +x Запуск.sh
./Запуск.sh
```

Скрипт сам переходит в свою папку (иначе программа не найдёт настроечный
файл), проверяет наличие Java и, если её нет или программа завершилась
с ошибкой, показывает сообщение окном – чтобы причина была видна и при
запуске двойным щелчком из файлового менеджера, без терминала. Команда
`./Запуск.sh --ярлык` создаёт значок программы в меню приложений и на
рабочем столе с эмблемой кафедры.

Настроечный файл называется кириллицей, а имена файлов Java читает
в кодировке, которую сообщает система. При локали не UTF-8 (например,
`LANG=C`) обращение по имени файла его не находит, поэтому программа
в таком случае отыскивает настроечный файл просмотром своей папки –
настроечным считается файл `*.properties`, содержащий хотя бы одну
известную настройку.

### Минимальная версия Java

Проект собирается с `maven.compiler.release = 8` (`pom.xml`): код не
использует ничего новее восьмой версии (что проверено компиляцией
с флагом `--release 8`, который следит не только за синтаксисом, но и
за тем, чтобы не вызывались API, добавленные позже), поэтому собранный
`upo-lab1.jar` запускается на любой Java 8 и новее.

Собрать под Java 7, 6 или 5 не получится: у этих версий давно закончилась
поддержка (Java 7 – с 2015 года, Java 6 – с 2013, Java 5 – с 2009), и их
компиляторов уже нет ни в одном актуальном источнике пакетов – проверено,
что современные JDK (в частности JDK 21, на котором собирается сам
проект) прямо отказываются компилировать код под них ("Source option 7
is no longer supported"). Раз таких компьютеров сегодня практически не
остаётся, гадать вслепую и собирать непроверенный jar под них не стали.

Если `Запуск.bat` всё же обнаружит слишком старую Java (исключение
`UnsupportedClassVersionError`), он сам покажет установленную версию
(`java -version`) прямо в консоли – её и нужно сообщить для пересборки
`pom.xml` под конкретную версию, если она всё-таки окажется ниже восьмой.

### Пакет математики

Всё, что считается в работе, собрано в пакете `math` и больше нигде не
повторяется. Его классы не знают ни об экранах программы, ни о рабочей
тетради, ни о файле исходных данных: на вход подаются числа, на выходе
получаются числа. Поэтому любую формулу можно проверить отдельно, не
запуская саму программу. В каждом классе описано, что именно в нём
считается, откуда взята формула и каким способом её проверить; готовый
набор таких проверок собран в `src/test/java/ru/vka/upo/math/MathCheck.java`:

```
javac -encoding UTF-8 -d target/check -cp target/classes \
      src/test/java/ru/vka/upo/math/MathCheck.java
java -cp target/classes:target/check ru.vka.upo.math.MathCheck
```

Проверяется, в частности: восстановление коэффициентов по измерениям,
точно лежащим на полиноме; совпадение корреляционной матрицы с прямым
обращением AᵀA; равенство случайной ошибки σ/√N при нулевой степени
полинома и её рост к краям выборки при большей степени; совпадение
производных с разностными отношениями; разметка выборок; дальность по
теореме косинусов; свойства шума измерений. Расчётное ядро `core` этой
математики не дублирует: оно собирает исходные данные в массивы, вызывает
формулы из `math` и раскладывает результат по строкам таблицы.

Формы сделаны на свободной компоновке (GroupLayout) – в том же виде, в каком
их пишет сам конструктор NetBeans. Панели, которые программа наполняет во
время работы (карточки экранов, варианты ответа), описаны в формах как пустые
контейнеры, а нужную раскладку им задаёт код вне блока `initComponents()`.

Каждой форме соответствует пара файлов: `.java` с блоком `initComponents()`,
который формирует визуальный конструктор, и `.form` с описанием формы.
Правки, сделанные мышью в конструкторе NetBeans, попадают в оба файла;
собственный код размещается вне блока `initComponents()`.

## Откуда берутся ошибки, выводимые в таблицу

Расчёт работы целиком аналитический, и так же он был устроен в прежней
программе: датчика случайных чисел в ней нет вовсе. Это установлено опытом
над `obr.exe`, а не предположено. Два независимых запуска с одинаковыми
исходными данными дают побитово одинаковые числа; при удвоении СКО измерения
дальности (с 10 до 20 м при m = 2, N = 25, T = 0,1 с, M0 = 1) динамическая
ошибка не меняется ни в одном разряде (0,8666 м), а случайная растёт ровно
вдвое (5,550 → 11,10 м), полная получается сложением по квадратам
(√(0,8666² + 5,550²) = 5,617 – ровно то, что печатает программа).

Отсюда следует, что:

* динамическая ошибка есть невязка аппроксимации **истинной, безошибочной**
  траектории полиномом – поэтому от СКО измерения она не зависит;
* случайная ошибка есть значение теоретической формулы раздела 4.2
  σ<sub>δr</sub>·√(aᵀ(t)(AᵀA)⁻¹a(t)) – поэтому СКО входит в неё линейно;
* шум к измерениям не подмешивается, метод статистических испытаний
  (Монте-Карло) не применяется.

Новая программа воспроизводит это в точности: `Processor` обращается к модели
движения за истинными значениями и случайных чисел не запрашивает, поэтому
таблица результатов строго воспроизводима.

Датчик случайных чисел (`math/Noise.java`) задействован в программе ровно
в одном месте – в показе единичного опыта (`core/Realization.java`, кнопка
«Другая реализация шума»), которого в прежней программе не было. Он сделан
для наглядности: видно, что отсчёты ложатся с разбросом, полином каждый раз
проходит иначе, а среднее и разброс по накопленным опытам сходятся к тем
самым ERD и ERS, что уже стоят в таблице. При нажатии кнопки меняются только
график «Измерения и аппроксимирующий полином» и подпись под графиками;
таблица результатов, чертёж пролёта и ход ошибок по интервалу усреднения
не меняются.

Подробнее – в записке «Откуда берутся ошибки в лабораторной работе».

### Сверка с методом Монте-Карло и настройка noise.montecarlo

То, что аналитический расчёт даёт тот же результат, что дал бы прямой
статистический эксперимент, не принято на веру, а проверено счётом:
класс `src/test/java/ru/vka/upo/math/MonteCarlo.java` для нескольких режимов
обработки набирает измерения датчиком случайных чисел с заданным СКО,
проводит по ним полином методом наименьших квадратов, берёт ошибку оценки
в момент привязки и повторяет это 200 000 раз; среднее и разброс по опытам
сравниваются с ERD и ERS из таблицы. Расхождение во всех проверенных
режимах не превышает статистической погрешности самого моделирования.
Математическое обоснование (метод наименьших квадратов линеен по
измерениям, поэтому α̂ = L·r<sub>ист</sub> + L·ξ, и оба слагаемых – это
ровно ERD и ERS) и полная таблица сверки – в записке «Аналитический
расчёт и метод Монте-Карло».

Запускается отдельно от программы, как и `MathCheck`:

```
javac -encoding UTF-8 -d target/check -cp target/classes \
      src/test/java/ru/vka/upo/math/MonteCarlo.java
java -cp target/classes:target/check ru.vka.upo.math.MonteCarlo
```

Тем же результатом объясняется и настройка `noise.montecarlo` в файле
настроек: при `true` таблица результатов (в режиме «в момент привязки»)
считается не по формулам, а тем же прямым моделированием, что и
в `MonteCarlo.java`, – `noise.trials` опытов на строку (по умолчанию
20000). Числа при этом получаются те же самые с точностью до статистической
погрешности, но со случайным дрожанием при разных запусках и с заметно
большим временем расчёта, поэтому в учебной работе эта настройка не нужна
и оставлена выключенной по умолчанию; сделана она как демонстрация
и как ещё один способ проверить программу, а не как более правильный
способ считать.

## Таблица вариантов

Встроены двадцать пять вариантов. Первые пять взяты из задания кафедры без
изменения, остальные двадцать получены полным перебором тех же значений трёх
параметров: СКО измерений (10, 15, 25, 35 и 50 м), высоты орбиты (1000, 800,
600, 400 и 300 км) и расстояния до трассы полёта (50, 100, 150, 200 и 250 км).
Расстояние до трассы расставлено по правилу латинского квадрата, так что
повторяющихся сочетаний в таблице нет, а каждое значение каждого параметра
встречается ровно пять раз. Двадцати пяти вариантов хватает на учебную группу.

Если рядом с программой положить файл
`Варианты.csv` (или `variants.csv`), таблица читается из него – варианты
можно менять без пересборки. Разделитель «;», десятичная запятая допускается,
строки с «#» пропускаются. Столбцы: номер; признак траектории (1 наземный,
2 бортовой); признак скорости (0 дальность, 1 скорость, 2 обе); интервал
измерений, с; высота орбиты, км; расстояние до трассы, км; траверзное
расстояние, км; СКО дальности, м; СКО скорости, м/с.

## Назначение варианта

Вариант обучающийся не выбирает: он назначается по номеру в журнале группы,
который обучающийся вводит на первом экране (`VariantTable.byListNumber`).
Номеров в журнале может быть больше, чем вариантов, поэтому счёт идёт
по кругу: номер 26 получает первый вариант, номер 27 – второй и так далее.
На экране ввода исходные данные варианта уже подставлены, а кнопка
«Загрузить заново» возвращает их, если обучающийся значения правил.

## Ввод исходных данных

Данные проверяются при каждом изменении, замечания выводятся в нижнем окне.
Замечания двух видов: препятствующие расчёту (кнопка расчёта становится
недоступной) и предупреждающие. Поля, не относящиеся к выбранному сочетанию
признаков траектории и измеряемых параметров, гаснут и обязательными
не считаются.

Значения режима обработки по умолчанию: степень полинома m = 2, объём
выборки N = 49, шаг измерений T = 0.1 с, момент привязки M0 = 25
(середина выборки); относительная скорость для бортового измерителя – 0.
Десятичный разделитель во всех полях и таблицах – точка; введённая
запятая приводится к точке при переходе к следующему полю.

## Входной контроль знаний

Банк содержит 18 вопросов. Формулировки и варианты ответов взяты
из прежней программы без изменения смысла: исправлены опечатки и приведена
к единому виду пунктуация. Номера правильных ответов установлены
экспериментально по отклику прежней программы, поэтому оценка выставляется
так же, как выставлялась раньше.

Обучающемуся предлагаются пять вопросов, за каждый правильный ответ
начисляется один балл, оценка равна числу баллов. К выполнению работы
допускаются набравшие не менее трёх баллов.

Отличие от прежней программы одно: набор из пяти вопросов отбирается
случайно. Раньше он жёстко определялся номером варианта и при каждом
запуске был одним и тем же, так что ответы легко заучивались.

## Что меняется в расчётах по сравнению с прежней программой

Подробное обоснование приведено в записке «О программе ЛР Предварительная
обработка». Кратко:

1. Все вычисления в двойной точности, вместо обращения матрицы нормальных
   уравнений применяется устойчивое ортогональное разложение.
2. Динамическая ошибка вычисляется по определению практикума, то есть
   в момент привязки оценки.
3. Введён контроль исходных данных: привязка в пределах выборки, степень
   полинома в пределах, допустимых при данном объёме выборки, и так далее.

На время отработки программы предусмотрен режим, точно воспроизводящий
поведение прежней программы (`Processor.setLegacy(true)`), для
автоматической сверки с эталонными расчётами. По завершении отработки
этот режим убирается.

## Расчётное ядро

Движение объекта воспроизводится так же, как в прежней программе:
круговая орбита заданной высоты, наземный пункт на заданном расстоянии
от трассы полёта, наибольшее сближение в середине интервала измерений,
вращение Земли не учитывается, радиус Земли 6371 км. Для бортового
измерителя – прямолинейное сближение с постоянной относительной
скоростью.

Выборка из N измерений с шагом T обрабатывается взвешенным методом
наименьших квадратов. Выводятся пять выборок, размещённых равномерно так,
чтобы каждая целиком лежала внутри интервала измерений: первая начинается
в его начале, последняя им заканчивается. (Прежняя программа брала начала
в точках k·T<sub>К</sub>/5, отчего последняя выборка выходила за интервал
измерений.) Случайная составляющая ошибки берётся из
корреляционной матрицы оценок, динамическая – как разность истинного
значения и значения аппроксимирующего полинома в момент привязки,
полная – корень из суммы квадратов.

## Сверка с прежней программой

Классы `src/test/java/.../ReferenceCheck.java` (сверка) и `Demo.java`
(пробный расчёт) в поставку не входят, они нужны только при отработке.
Сверка сопоставляет расчёт в режиме совместимости с эталонным прогоном
прежней программы по всем десяти вариантам (920 строк таблиц):

```
java -cp target/classes:target/test-classes ru.vka.upo.core.ReferenceCheck Эталон_ЛР1_полные_таблицы.csv
```

Результат сверки:

* случайная составляющая – 1790 значений, наибольшее расхождение 0,044 %;
* динамическая составляющая – совпадение в пределах 1,5 % везде, где
  прежняя программа выдавала достоверные значения (больше сотни метров
  или метров в секунду). Ниже этого уровня у неё сказывается собственная
  вычислительная погрешность одинарной точности: например, при шаге
  измерений 0,01 с она печатает динамическую ошибку скорости в единицы
  метров в секунду там, где истинное значение – миллионные доли.

Сверка подтвердила и то, о чём говорилось выше: динамическая ошибка
прежней программы – это средняя квадратическая невязка аппроксимации на
всём интервале усреднения, поэтому она и не зависела от номера точки
привязки M0.

## Ход ошибок по интервалу усреднения

Третий рисунок на экране результатов показывает обе составляющие ошибки как
функции времени внутри выборки (`ErrorProfile`, `ErrorView`):

* сплошная линия – динамическая ошибка Δ(t) = r(t) – r̂(t) при отсутствии
  шумов измерений. Руководство к работе определяет её именно так, для
  произвольного момента времени, а в таблицу выводится её значение в момент
  привязки;
* светлая полоса – коридор ±σ(t), где σ²(t) = aᵀ(t)·K·a(t), K – корреляционная
  матрица ошибок коэффициентов, a(t) – вектор степеней нормированного времени.

В момент привязки эти величины в точности равны ERD и ERS выбранной строки
таблицы, поэтому рисунок прямо связан с расчётом. Из него видно и то, почему
момент привязки важен: коридор случайной ошибки уже всего вблизи середины
выборки и заметно расширяется к её краям, а динамическая ошибка знакопеременна
и обращается в ноль в нескольких точках интервала, так что её значение
в привязке зависит от того, куда эта привязка попала.

## Способ вычисления динамической ошибки

Настройка `error.mode` в файле «Настройки.properties» задаёт один из трёх
режимов (`Processor.Mode`); на экране преподавателя режим можно сменить
и на ходу:

| Значение | Динамическая ошибка | Размещение выборок | Арифметика |
|---|---|---|---|
| `anchor` (по умолчанию) | в момент привязки, по руководству | внутри интервала измерений | двойная точность, ортогональное разложение |
| `averaged` | средняя квадратическая невязка по интервалу усреднения | по разметке прежней программы | двойная точность |
| `legacy` | то же | по разметке прежней программы | нормальные уравнения и невязки в одинарной точности |

Режим `averaged` совпадает с прежней программой всюду, где та считала
достоверно: случайная составляющая – 1790 значений, наибольшее расхождение
0,044 %; динамическая при значениях свыше 20 м – 326 из 330 значений
в пределах 2 %.

### Разметка выборок прежней программы

Прежняя программа отсчитывала начало k-й выборки не по времени, а по номеру
измерения: шаг между выборками равен целому числу измерений
INT(T<sub>К</sub>/5/T), а сам момент набирается накоплением шага T
в одинарной точности. Поэтому начала выборок слегка смещены относительно
k·T<sub>К</sub>/5 (при T = 0,1 с шаг получается 35,9 с вместо 36 с), а на
мелком шаге добавляется дрейф накопления (при T = 0,01 с последняя выборка
начинается в 179,98 с). Выборку, не укладывающуюся в запас 1,2·T<sub>К</sub>,
прежняя программа не считала вовсе, поэтому при больших N таблица содержит
не пять строк, а четыре. Всё это восстановлено по прогонам самой прежней
программы (проверено на 20 сочетаниях T<sub>К</sub>, T, N и M0, расхождений
нет) и воспроизводится в режимах `averaged` и `legacy`.

### Что в режиме `legacy` совпадает, а что нет

Совпадает точно: моменты времени в таблице, число выводимых строк, случайные
составляющие ERS и EVS, а также независимость динамической ошибки от момента
привязки (прежняя программа при M0 = 5, 13, 25, 37, 49 выдаёт одни и те же
значения ERD, и наш режим теперь тоже). При степенях полинома 0 и 1, где
динамическая ошибка настоящая, совпадение полное.

Совпадает только по порядку величины сама «полка» при степени 2 и выше. Там
результат определяется не формулой, а конкретной вычислительной погрешностью
фортрановских подпрограмм: наша «полка» примерно вдвое ниже. Повторить её
поразрядно без исходного текста прежней программы нельзя, и на существо дела
это не влияет: и там, и там вместо динамической ошибки выводится собственная
погрешность вычислений.

## Перенос чисел в рабочую тетрадь

По умолчанию программа в тетрадь ничего не записывает: числа обучающийся
переписывает сам, как переписывал бы их в тетрадь на бумаге. Настройка
`notebook.transfer = true` в файле `Настройки.properties` включает перенос
мышью: щелчок правой кнопкой по строке таблицы результатов открывает меню,
из которого ERD, ERS и ER этой строки заносятся в таблицу выбранного пункта
задания.

Пункт выбирается вручную, и это не упущение: один и тот же режим обработки
может относиться к разным пунктам – например, m = 3, N = 49, T = 1 с,
M0 = 25 подходит и под пункт б (там меняется T, а M0 = 25 закреплено),
и под пункт г (там меняется M0, а T = 1 с закреплено). Программа лишь
выделяет в меню тот пункт, которому заданный режим отвечает по закреплённым
параметрам. Строка тетради определяется значением изменяемого параметра;
если обучающийся взял значение, не предусмотренное заданием, строка для
него заводится и встаёт на своё место по возрастанию.

Перенос предназначен для занятий, где важно успеть пройти все четыре
пункта, и для показа работы преподавателем. Сверка занесённых чисел
с расчётом при этом продолжает работать: она сравнивает числа тетради
с той строкой таблицы, из которой они взяты.

## Порядок работы обучающегося

1. Вход: фамилия с инициалами, учебная группа, номер по списку в журнале.
   Вариант назначается по номеру, выбрать его нельзя. С экрана входа
   открывается окно «Задание на работу»: порядок выполнения и содержание
   пунктов следует прочитать до начала расчётов.
2. Входной контроль знаний: пять вопросов, к работе допускаются набравшие
   не менее трёх баллов.
3. Ввод исходных данных и параметров режима обработки.
4. Расчёт: таблица ошибок по пяти выборкам и три иллюстрации – чертёж
   пролёта, ход дальности с измерениями и аппроксимирующей кривой и ход
   обеих составляющих ошибки по интервалу усреднения. Кнопка «Другая
   реализация шума» (под иллюстрациями) показывает, что при том же режиме
   меняется от опыта к опыту, а что остаётся: числа в таблице не меняются,
   меняются только график измерений и подпись со статистикой опытов под
   графиками. Кнопка «Параметры режима обработки» – рядом с таблицей
   результатов. Нижний ряд кнопок экрана отведён только под переходы между
   экранами: «К вводу данных», «Задание на работу», «Сведения из теории»,
   «В рабочую тетрадь».
5. Рабочая тетрадь: обучающийся сам переносит числа в таблицу пункта задания,
   строит по ним график и пишет вывод.
6. Отчёт в файле Word: шапка, исходные данные, все четыре таблицы,
   графики и выводы. Шрифт отчёта – Times New Roman, 12 пт, одинарный
   межстрочный интервал (`DocxWriter`, `word/styles.xml`).

Готовых зависимостей ошибки от параметров режима программа обучающемуся
не показывает: их он получает сам, прогоняя режимы один за другим.
Программа берёт на себя только черчение и мягкую проверку – выпадающая
из ряда точка подсвечивается словами «проверьте переписанное», правильное
значение при этом не показывается.

## Окно программы

Вид главного окна задаётся настройкой `window.fullscreen` в файле
`Настройки.properties`.

По умолчанию (`window.fullscreen = true`, либо настройка вообще не задана)
окно открывается на весь экран, поверх панели задач, без рамки и системных
кнопок (свернуть/развернуть/закрыть); изменить его размер нельзя. Завершить
работу можно только кнопкой «Выход» в правом верхнем углу – она есть на
любом экране программы и выводит то же подтверждение, что несохранённые
результаты расчёта и записи рабочей тетради будут потеряны. Системное
закрытие окна (Alt+F4 и т. п.) не действует. Такой режим рассчитан на
учебный терминал, с которого не должно быть случайного выхода на рабочий
стол во время контрольной работы.

При `window.fullscreen = false` окно открывается как обычное: с заголовком
и системными кнопками, сворачивается, разворачивается, изменяется в
размерах и центрируется на экране. Закрыть его можно и крестом в
заголовке, и кнопкой «Выход» – в обоих случаях с одним и тем же
подтверждением о потере несохранённых результатов.

### Окна «Задание на работу», «Сведения из теории» и четыре графика

`TaskFrame`, `HelpFrame` и `SummaryFrame` ведут себя как модальные, хотя
и не по отношению ко всей системе (не `setAlwaysOnTop(true)` навсегда –
иначе стало бы невозможно переключиться на другую программу), а только
по отношению к главному окну: одновременно открыт только один экземпляр
каждого окна (повторное открытие просто выводит уже открытое на передний
план), а главное окно на время их показа отключается (`setEnabled(false)`)
и включается обратно при закрытии. Свернуть эти окна нельзя: попытка
(системной кнопкой, если она есть, или сочетанием клавиш) сразу
отменяется, и выводится сообщение «Это окно нельзя свернуть, можно только
закрыть» – без такого сообщения было непонятно, почему окно тут же
разворачивается обратно.

В полноэкранном режиме главного окна (`window.fullscreen = true`) эти
окна тоже открываются без рамки и на весь экран. Так как в этом режиме
само главное окно постоянно держит признак «поверх всех окон» (см. выше –
это сделано намеренно, чтобы с учебного терминала нельзя было случайно
переключиться на рабочий стол), окну-«диалогу» приходится
делать то же самое: при открытии оно тоже включает у себя `setAlwaysOnTop`
и не снимает этот признак, пока не будет закрыто – иначе главное окно
тут же перекрывало бы его собой. В обычном (не полноэкранном) режиме
это не нужно: там признак включается лишь на мгновение при открытии
(чтобы надёжно вывести окно поверх), а затем сразу снимается.

Кнопка «Открыть в браузере» (у «Задания на работу» и «Сведений из
теории») в полноэкранном режиме не показывается: она там не имеет смысла
– и без того всё видно на весь экран, а сам браузер, если его открыть,
всё равно окажется позади главного окна и будет недоступен.

## Режим преподавателя

Вход по паролю, который задаётся в файле `Настройки.properties` рядом
с программой (`teacher.password`, по умолчанию `kaf33`). Открывает расчёт
всех пунктов задания сразу, с выгрузкой таблицы в CSV, и выбор способа
вычисления динамической ошибки – для сверки с эталонными расчётами.

При переходе в поле пароля раскладка клавиатуры переключается на
английскую автоматически (`LoginPanel`, `pwdTeacher.getInputContext()
.selectInputMethod(Locale.ENGLISH)`): в полноэкранном режиме индикатора
текущей раскладки не видно, и при неверно набранном пароле было непонятно,
то ли ошибка в самом пароле, то ли просто была включена русская раскладка.

Кнопка «Построить зависимости по всем пунктам» показывает в отдельном окне
готовые зависимости ошибок от параметров режима обработки: четыре графика
и четыре таблицы, по одному на каждый пункт задания. Расчёт ведётся строго
по руководству к работе: числа берутся из первой строки таблицы результатов
(п. 4.3), а степень полинома для пунктов б, в и г не задаётся произвольно,
а определяется по пункту а – берётся та, при которой полная ошибка дальности
оказалась наименьшей. Найденная степень выведена в шапке окна.

Обучающемуся этот экран недоступен намеренно: смысл работы в том, чтобы
прогонять режимы по одному, выписывать числа и строить эти зависимости
самому.

Это не то же самое, что «работа без входного контроля» у обучающегося:
режим преподавателя – отдельная роль для проверочного расчёта всех
пунктов задания сразу (входа по паролю, а не по фамилии и группе, и без
отчёта), а не способ провести обычную студенческую работу без контроля.
Для этого есть отдельная настройка `test.enabled` (см. ниже).

## Входной контроль знаний

Настройка `test.enabled` в `Настройки.properties`:

- `true` (по умолчанию) – после экрана приветствия обучающийся проходит
  контроль (пять вопросов по теории, минимум три балла для допуска
  к работе), как предусмотрено методикой. Полученная оценка попадает
  в шапку отчёта строкой «Оценка за входной контроль».
- `false` – экран контроля пропускается, обучающийся сразу переходит
  к вводу исходных данных; в отчёте вместо оценки пишется, что входной
  контроль не проводился.

## Доделки

- На графике «Ход ошибок по интервалу усреднения» (ErrorView) сделать
  автоматическую подрезку вертикальной оси по коридору ±σ(t): сейчас на
  режимах с малой степенью полинома у краёв интервала (где Δ(t) уходит на
  порядки больше σ(t) – например, m = 0 на первой/пятой выборке) коридор
  случайной ошибки схлопывается в невидимую полоску. Ось предлагается
  масштабировать по σ(t) (плюс само значение Δ(t₀) в привязке), а участки
  кривой Δ(t), выходящие за пределы видимой области, обрезать засечкой
  с подписанным числом – чтобы было видно и коридор, и то, что реальный
  размах ошибки на краях окна намного больше.
